## سياقات الاختبار الناجحة

- لا يمكن لمالك `atlas-demo` الاطلاع على موظفي `cedar-demo` رغم وجودهما في
  قاعدة بيانات واحدة، وتظهر قوائم بنتيجتين مختلفتين.
- لا تُصدَّر كلمة مرور العرض إلى ملف ولا تُطبع؛ يطلبها CLI عبر `getpass`.
- لا يغيّر أداة إنشاء العرض قاعدة بيانات موجودة ولا تعمل عند وضع الإنتاج.
- اختبارات المراحل السابقة للتحقق من الرموز، الدعوات، الجلسات، الصلاحيات،
  العزل وتقييد معدلات الطلبات ما زالت ضمن مجموعة الاختبارات الناجحة.

## محاذير قبل اعتبار GitHub Portfolio جاهزًا

1. تثبيت Flutter وتشغيل `flutter pub get`, `flutter analyze`, `flutter test`،
   ثم تنفيذ بناء Web وAndroid وiOS وفتح التطبيق فعليًا.
2. ربط مستودع GitHub مستقل وتشغيل وظائف CI، ومعالجة أي فشل يتم تسجيله.
3. التقاط الصور من التطبيق الحقيقي بعد اختبار RTL وLTR والتصفّح على الهاتف.
4. إنجاز الترجمة الكاملة للحوارات والإشعارات المتبقية والتحقق من الوصولية.
5. إجراء مراجعة أسرار وتاريخ commits وحقوق الملفات قبل جعل المستودع عامًا.

**الحكم:** مصدر المرحلة السابعة قابل للتسليم والمراجعة، لكن لا يوجد أساس
موضوعي لإعلان أن نسخة Android/iOS/Web اجتازت اختبارات البناء أو أن المنتج
أصبح جاهزًا لاستضافة بيانات موظفين حقيقية.
